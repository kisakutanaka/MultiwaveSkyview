# Gaia等級フィルタ・ラスター化パイプライン計画

## 背景

現行の`02_visible_gaia_dr3_density`は`CDS/P/DM/I/355/gaiadr3`(CDS製の
星密度マップHiPS)を`download_allsky_fits.py`経由で取得している。これは
各ピクセルが範囲内の星の「数」を集計した値であり、個々の星の等級情報は
取得時点で既に失われている。そのため`fits_studio.py`側で等級による
足切り(例: G<12の明るい星だけを表示)を後から行うことはできない。

等級フィルタを実現するには、CDSの既製ラスター画像を使う現行方式ではなく、
Gaia DR3カタログ自体をTAP経由でクエリし、フィルタした星のリストから
自前でラスター画像を作る新しいパイプラインが必要。

## 座標系の制約

既存パイプライン(`allsky_surveys.build_car_wcs`)は銀河座標
(`GLON-CAR`/`GLAT-CAR`)、8192×4096のplate carrée投影で統一されている。
新しいGaiaラスターもこれに合わせて銀河座標CARグリッドで出力する。

## スモールステップ

1. **TAP疎通確認** — `astroquery.gaia`で小さいクエリ(例: G<6の明るい星、
   数千件)を投げ、非同期ジョブが必要か・レスポンス時間はどれくらいかを
   確認する使い捨てスクリプト。
2. **座標変換の確認** — 取得したRA/Decを`build_car_wcs`と同じ銀河座標CAR
   グリッドのピクセル座標に変換する関数を書き、既知の明るい星(シリウス
   など)が正しい位置に来るか単体で検証。
3. **素朴なラスタライズ** — 明るい星だけ(G<6程度)を1ピクセル=1カウント
   で塗るだけの最小実装。8192×4096のFITSとして書き出し、見慣れた星座の
   形が見えるか目視確認。
4. **等級の重み付け** — フラックス換算(10^(-0.4×mag))かガウシアンPSFで、
   明るい星が大きく/明るく見える描画方式を試作し、単純な二値プロットと
   見比べる。
5. **本番の等級カットでの件数見積もり** — 実際に使いたいカット(例:
   G<12〜14)でのクエリ件数・データ量・クエリ時間を確認し、全件取得が
   現実的か判断。
6. **カタログ取得スクリプト化** — TAPクエリ結果をCSV/Parquetとして
   キャッシュ保存する`download_gaia_catalog.py`的なスクリプトを作成
   (再クエリを避けるため)。
7. **FITSラスター生成スクリプト** — 保存済みカタログから8192×4096 FITSを
   生成し、`allsky_textures/fits/`に保存(`convert_allsky_png.py`と同じ
   立ち位置)。
8. **SURVEYS登録** — `allsky_surveys.py`/`fits_studio.py`の
   `SURVEY_HINTS`に新エントリを追加し、`fits_studio.py`で他サーベイと
   同じようにプレビュー・調整できるようにする。
9. **見た目の確認・比較** — 既存の密度マップ版と見比べて、等級フィルタ版
   がちゃんと「写真っぽい」見た目になっているか確認。
10. (任意) 複数の等級カットバリエーションを用意して比較できるようにする。

## ステップ1の結果 (TAP疎通確認)

- `astroquery.gaia.Gaia.launch_job()`(同期)は**サーバー側でMAXREC=2000行に
  自動制限される**ことを確認(`Gaia.ROW_LIMIT`のクライアント側属性=50とは
  別物で、これは効かなかった)。件数を数えるだけの`COUNT(*)`クエリなら
  同期で十分だが、実データを取得する本番クエリは`launch_job_async()`を
  使う必要がある。
- `launch_job_async()`でG<6(6,764件)を6.5秒で全件取得できることを確認。
  非同期ジョブは2000行の制限を受けない。
- 等級カットごとの件数感(`COUNT(*)`のみ、軽量):
  - G < 8: 62,723件
  - G < 10: 482,106件
  - G < 12: 3,087,821件
  - G < 14: 16,844,156件
  - (参考: G < 6は6,764件、裸眼限界等級〜6.5等に近い規模)
- 目的が「クリアな肉眼での天体写真」であることを踏まえると、G<8〜10程度の
  カットで十分裸眼の見た目に近づけそうで、件数的にも軽量(数万〜数十万件)。
  G<12以降は数百万〜千万件超と桁違いに重くなるため、深追いしすぎない方針で
  進める。

## ステップ2の結果 (座標変換の確認)

`build_car_wcs`と同じヘッダ(GLON-CAR/GLAT-CAR、8192×4096)を`astropy.wcs.WCS`
に渡し、シリウス(RA=101.287155, Dec=-16.716116, J2000)を銀河座標
(l=227.230, b=-8.890)経由でピクセル座標(7116.7, 1845.2)に変換。既存の
DSS2赤画像FITSでそのピクセル値を見ると23394(画像平均2086の約11倍)と、
狙った位置に実際の輝星が写っていることを確認 — 変換が正しいことを実データで
検証できた。

## ステップ3の結果 (素朴なラスタライズ)

G<6(6,764件)を1ピクセル=1点で描画。全天プレビューでは銀河面(b=0付近)に
星が集中する傾向を確認。オリオン座付近を切り出し、有名な7星(ベテルギウス・
リゲル・ベラトリックス・ミンタカ・アルニラム・アルニタク・サイフ)だけを
個別プロットしたところ、三ツ星が一直線に並ぶなど実際のオリオン座の形と
矛盾しないことを確認 — 座標変換〜描画のパイプライン全体が正しく動作。

## ステップ4の結果 (等級の重み付け)

G<8(62,723件)のオリオン座付近クロップで、二値プロット(全星が同じ1点)と、
等級をフラックス換算しGaussian PSFで加算描画する方式を比較。
`flux = 10^(-0.4*(mag-8))`、`sigma = clip(0.9 + 0.4*(8-mag), 0.9, 6.0)px`で
明るい星ほど大きく/明るく滲むようにし、最終的にasinhストレッチ
(`image_processing.stretch_image`と同系)で圧縮。二値プロットが均一な点の
羅列にしか見えないのに対し、PSF版は明るい星が大きな円盤状に、暗い星は
小さな点になり、肉眼での星空写真に近い見た目になることを確認。
検証画像: https://claude.ai/code/artifact/76060435-596c-4739-83ac-ecd508b59513

## ステップ5の結果 (本番の等級カットでの件数見積もり)

G<10(482,106件、ra/dec/phot_g_mean_magの3カラムのみ)を`launch_job_async()`
で実測: 54.7秒、メモリ上のサイズは約9.6MB。ダウンロード・メモリの両面で
十分軽量。

**本番の等級カットはG<10を採用**する方針。裸眼限界(G<6〜7)より少し深く
取ることで星の密度に厚みが出て写真的な見た目になりつつ、G<12以降(300万件
超)のような重さは避けられる。将来もっと深くしたくなった場合の参考値も
記録しておく: G<12は約309万件、G<14は約1684万件(ステップ1で計測済み)。

## 解決済み: 最も明るい肉眼等級の星の等級が信用できない問題

`docs/gaia-data-fields-examples.md`で確認した通り、Gaiaは検出器が明るすぎる
星(目安G≲3等)で飽和し、`phot_g_mean_mag`が実際より大幅に暗く記録される
(シリウス: 実際は-1.46等のはずがGaiaでは8.52等、ベテルギウスは検索範囲内に
本来の記録が見当たらず無関係な暗い星がヒット)。

**対処**: `download_bright_star_catalog.py`を新規作成し、VizieRのYale Bright
Star Catalogue(V/50、Vmag<3.5、285件)を取得。`rasterize_gaia_catalog.py`に
`merge_bright_stars()`を追加し、Gaiaカタログの星のうち補完カタログの星と
位置が30秒角以内で一致するものを正しいV等級のレコードで置き換えてから
ラスタライズするようにした(285件中219件が置換、66件は新規追加)。

再ラスタライズして確認したところ、ベテルギウス・リゲルが三ツ星より明確に
明るく、シリウスも堂々とした大きな円盤として描かれるようになった — 実際の
夜空の見た目と一致する。検証画像は以下のレポートに追記済み:
https://claude.ai/code/artifact/76060435-596c-4739-83ac-ecd508b59513

## ステップ6の結果 (カタログ取得スクリプト化)

`download_gaia_catalog.py`を作成(`download_allsky_fits.py`と同じCLI流儀:
`--mag-limit`(デフォルト10.0)、`--force`、既存ファイルは自動スキップ)。
`ra,dec,phot_g_mean_mag`の3カラムをCSVにキャッシュする方式にした
(pandas/pyarrow等の新規依存を避け、`astropy.table.Table.write`で完結)。
実行してG<10の実データを取得: `allsky_textures/gaia_catalog/gaia_dr3_g10.csv`
(482,106行、25MB)。再実行時にskipされることも確認済み。
`allsky_textures/gaia_catalog/`は`.gitignore`に追加(FITS生データと同様、
再生成可能なのでコミット不要)。

## ステップ7の結果 (FITSラスター生成スクリプト)

`rasterize_gaia_catalog.py`を作成。CSVカタログを読み込み、ステップ4で
検証したGaussian PSF式(`flux = 10^(-0.4*(mag-mag_limit))`,
`sigma = clip(0.9 + 0.4*(mag_limit-mag), 0.9, 6.0)`)で8192×4096の
CARグリッド全体にラスタライズし、`build_car_wcs`と同じWCSヘッダを持つ
FITSとして`allsky_textures/fits/02e_visible_gaia_dr3_mag.fits`に保存する
(他サーベイと同じ立ち位置)。

実行結果: 482,106個の星を**3.6秒**でラスタライズ(事前の懸念に反して
Pythonループでも十分高速だった)、出力128MB。全天プレビュー(2K)を目視
確認したところ、銀河面の帯と星の密度分布が自然で、明るい星が大きく
写る「写真的な」見た目になっていることを確認 — 密度マップ版
(`02_visible_gaia_dr3_density`)より明確に良い。

## ステップ8の結果 (SURVEYS登録)

`allsky_surveys.SURVEYS`に`02e_visible_gaia_dr3_mag`を追加(`hips`キーは
持たせず、代わりに`download_allsky_fits.py`側に「`hips`キーが無い
サーベイはスキップする」ガードを追加 — hips2fits経由ではなく
`download_gaia_catalog.py`+`rasterize_gaia_catalog.py`という別パイプラインで
作られるため)。`fits_studio.py`の`SURVEY_HINTS`にも解説を追加し、
02の密度マップの制限(等級情報が失われている)への回答であること、
Gaiaの明るい星飽和問題(将来課題)への言及を含めた。

## ステップ9の結果 (見た目の確認・比較)

既存の密度マップ版(`02_visible_gaia_dr3_density`)と新しい等級重み付け版
(`02e_visible_gaia_dr3_mag`)を同条件で比較。銀河面付近では密度マップも
滑らかな拡散光としてそれらしく見える(マゼラン雲まで写る)が、銀河面から
外れたオリオン座周辺を拡大すると差が決定的: 密度マップ版はほぼノイズにしか
見えない一方、等級重み付け版は明瞭な星空になる。

**結論**: 個々の星・星座の再現(今回の目的「クリアな肉眼での天体写真」に
直結)には等級重み付け版が明確に優位。ただし密度マップ版が持つ銀河面の
なめらかな拡散光(無数の未分解の淡い星が作る"glow")は等級重み付け版には
無い — 将来的に両者を合成する余地はあるが、今回のスコープ外とする。

https://claude.ai/code/artifact/76060435-596c-4739-83ac-ecd508b59513
