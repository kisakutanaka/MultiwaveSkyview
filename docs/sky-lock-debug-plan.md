# 「実際の空と同期」モード カメラ挙動バグ 切り分け計画

## 症状の経緯

1. **初回報告**: 実機(iPhone)で有効化すると、実際のスマホの動きに反してカメラの向きが
   「グリングリン」変わる。単純な反転ではなく、あちこちに飛ぶような動き。
   - 原因候補として特定・修正: iOSの`webkitCompassHeading`は無効値のとき`-1`を返す仕様が
     あり、`sensors/deviceOrientation.ts`の`resolveAlphaDeg`がこれを有効な方位として
     扱っていた(`alpha = 360 - (-1) = 361°`にジャンプ)。`iosHeading >= 0`のチェックを追加。
   - あわせてカメラ向きの反映をslerpで滑らかにする平滑化(`SMOOTHING_FACTOR`)を追加。

2. **2回目の報告**: 上記修正後、今度は「視点が定期的にどこかに戻される」症状。
   - 原因を特定・修正: `main.ts`の`animate()`では`controls.update()`(OrbitControls)が
     `skyLock.update()`より先に呼ばれる。`OrbitControls.update()`は`enabled=false`でも
     毎フレーム自分の内部状態でカメラの向きを強制的に上書きするため、
     `camera.quaternion`を起点にslerpしていた実装は、毎フレーム
     「OrbitControlsが凍結している古い向き」から20%だけ動く→次フレームでまた
     引き戻される、を繰り返していた。
   - 修正: `SkyLockController`内部に独立した`currentQuaternion`を持たせ、そちらをslerpし、
     `controls.update()`の後で`camera.quaternion`に強制上書きする形に変更
     (`skyLock.ts`)。

3. **3回目の報告(今回)**: それでも南に固定されたり、自由視点から切り替えた瞬間の
   カメラの向きに引きずられているような挙動が見える。

## ユーザーの仮説

- 初期姿勢定義の実装が違う
- 回転の計算方法が違う
- センサから取得した値の反映方法が違う

## 方針: スモールステップでの切り分け

これまで2回、「直したつもりが実は別の場所で干渉していた」を繰り返しているため、
パイプライン全体を一度に検証するのをやめ、各段階を独立に(前後の段階に依存せず)
個別に検証できるデバッグUIを用意して、どの段階に問題があるかを一つずつ確定させる。

```
[1] センサー生値 (alpha/beta/gamma, webkitCompassHeading)
        │
[2] 方位角のみ (azDeg) ← 現在ここを検証中
        │
[3] 高度角込みの姿勢 (altDeg, azDeg)
        │
[4] AltAz → 赤道座標 → 銀河座標 → ワールド方向 (astro/, galacticToDirection.ts)
        │
[5] カメラへの反映 (quaternion適用・平滑化・OrbitControlsとの干渉)
```

### ステップ1(実装済み): 方位角(azimuth)のみを単体検証

ジオロケーション・銀河座標変換・カメラを一切介さず、「センサーの生値から
正しく方位を読み取れているか」だけを確認する最小テストパネルを追加した。

- `viewer/src/ui/headingCheckPanel.ts`(新規)
- 画面右下に「方位チェック開始」ボタンが表示される(`isDeviceOrientationSupported()`
  の場合のみ)。位置情報の許可は不要。
- 押すとDeviceOrientation権限のみをリクエストし、以下をリアルタイム表示:
  - 計算結果: `N (12°)` のような大きな表示(`sensors/deviceOrientation.ts`の
    `computeAltAz`が出す`azDeg`を16方位に丸めたもの)
  - 詳細行: `webkitCompassHeading(raw)` / `alpha(raw)` / `beta` / `gamma` / `absolute`

**確認方法**: 実際に北・東・南・西を向いて(方位アプリ等の既知の基準と比較しながら)、
表示される方位が実際の向きと一致するかを見る。

- 一致する → ステップ[1]〜[2]は正しい。次はステップ3(仰角込み)、
  ステップ4(座標変換)を疑う。
- 一致しない → `computeAltAz`のオイラー角/クォータニオン構成
  (`deviceOrientation.ts`の`SCREEN_TO_CAMERA`や`"YXZ"`の並び)か、
  `resolveAlphaDeg`の符号・基準がそもそも間違っている可能性が高い。

**結果(確認済み)**: 方位角は正しく反映されており、スマホのtiltを変えても
azDegの計算は崩れない。→ ステップ[1]〜[2]の方位角部分は正しいと確定。
次は仰角(altDeg)とステップ3(座標変換)・ステップ4/5(カメラ反映)を疑う。

### ステップ2(実装済み): 仰角込みの姿勢を単体検証

ステップ1のパネル(`headingCheckPanel.ts`)に`altDeg`の表示を追加した
(「方位 N (0°)」の下に「仰角 45°」のように表示)。

**確認方法**: スマホを水平(仰角0°付近)・真上(仰角90°付近)・斜め約45°に向けて、
表示される仰角が直感と一致するかを見る。あわせて、方位角がこれまで通り正しいままか
(ステップ1の結果が仰角の追加で崩れていないか)も確認する。

**結果(確認済み)**: 仰角も正しく反映されている。→ ステップ[1]〜[2]
(センサー→AltAz)は完全に確定。`SkyLockController`も`headingCheckPanel`と
全く同じ`computeAltAz`/`DeviceOrientationTracker`を使っているため、この確認は
`skyLock.ts`側の入力にもそのまま当てはまる。

### ステップ3・4(検証済み): 座標変換パイプライン (AltAz→赤道座標→銀河座標)

実機を使わず、astropy(正解が保証された天文計算ライブラリ)と自前のTS実装を
同一入力(緯度35.681236 / 経度139.767125 / 2026-07-27T12:00:00Z / 複数のalt,az点)
で突き合わせて検証した(スクリプトは一時ディレクトリ、結果は下記)。

```
                自前TS実装                          astropy(正解)
N horizon  alt=0 az=0 -> l=157.5263 b=12.1663    l=157.3770 b=11.8875
E horizon  alt=0 az=90 -> l=87.6049 b=-57.8719   l=86.9072 b=-57.8212
S horizon  alt=0 az=180-> l=337.5263 b=-12.1663  l=337.3759 b=-11.8779
W horizon  alt=0 az=270-> l=267.6049 b=57.8719   l=266.9203 b=57.8225
Zenith     alt=90 az=0 -> l=60.5982 b=29.2271    l=60.5584 b=29.4189
```

差は0.1〜0.5°程度。これは`astro/coords.ts`のコメントに元々明記されている
「歳差・章動補正なし」という意図的な近似の範囲内(J2000から2026年まで約26年分の
歳差 ≈ 0.3〜0.5°とちょうど符合する)。

**結果**: ステップ3・4(`astro/time.ts`, `astro/coords.ts`、AltAz→赤道座標→銀河座標)
は正しいと確定。ただしこれは「銀河座標(l, b)が正しく求まっているか」までの検証で、
その先の「銀河座標を実際にThree.jsのワールド方向(=テクスチャ上のどこを指すか)に
変換する`galacticToDirection.ts`」は別物であり、ここは含まれていなかった。

### ステップ4b(バグ発見・修正済み): 銀河座標 → Three.jsワールド方向

ユーザーから「コンパスリングの位置が依然として正しくない。数値表示だけは正しい」
との報告を受け、`galacticToDirection.ts`のコメントに書かれていた導出過程を
精査したところ、**FITS→PNG移行前の前提のまま更新されていなかった**ことが判明した。

- 移行前: ブラウザで直接FITSをパースし`THREE.DataTexture`(`flipY=false`)に
  アップロードしていた。この場合、テクスチャ座標v=0が北(GLAT=+90)に対応する。
- 移行後(現在): `convert_allsky_png.py`がPython側で`np.flipud`により北を
  PNGの上端に配置し、それを`textures.ts`が`THREE.Texture`(**デフォルトの
  `flipY=true`のまま、未設定**)でアップロードする。この場合、テクスチャ座標
  v=1が北(GLAT=+90)に対応する。**v↔GLATの対応が移行前と逆転していた。**

`SphereGeometry`のソース(`uvs.push(u+uOffset, 1-v)`, `theta=(iy/heightSegments)*PI`)
を直接読んで手計算すると、正しい`theta`は`PI*(90-GLAT)/180`であるべきところ、
コードは移行前のままの`PI*(GLAT+90)/180`(南北180°反転した式)になっていた。
これが北緯側と南緯側を入れ替えてしまうバグの正体で、
「コンパスリングの位置が正しくない」という症状と一致する。

**この式が実際に間違っていたことの検証**: 一時的に旧式に戻し、`b=+80`(北極寄り、
North Polar Spurが見えるはず)を`__skyLockDebug.lookAtGalactic(0, 80)`で
確認したところ、旧式では「新式で`b=-80`(閑散とした南天)を見たときと全く同じ、
何もない静かな空」が表示された。南北が入れ替わっていたことが視覚的にも確定した。

**修正**: `theta = ((90 - bDeg) / 180) * Math.PI`に変更(`viewer/src/astro/galacticToDirection.ts`)。
`phi`(経度方向)は移行の影響を受けていないため変更なし。
コメントも現在のパイプラインに合わせて全面的に書き直した。

なお、この`galacticToDirection.ts`は「実際の空と同期」機能(と検証用コンパス
リング)専用の逆変換であり、通常のサーベイ表示(球体テクスチャそのもの)は
ジオメトリのUVを直接使うだけでこの関数を経由しないため、このバグは
サーベイの見え方には影響していなかった。だからこそ、通常表示のPlaywright
スクリーンショットレビューでは一度も気づかれなかった。

### 新たな報告: E/W・N/Sが逆転している

ステップ4b修正後、再テストしたところ「コンパスリングのEはW、SはNに見える」との
報告。E↔W・N↔Sが対で入れ替わるパターンは、方位角に一律+180°のオフセットが
掛かっているのと等価な症状で、これは以下のどちらでも起こり得る:

- (a) リング自体(`galacticToWorldDirection`のphi、あるいは`altAzToEquatorial`)の
  バグ。ただしphiの式は`SphereGeometry`のソースから独立に再導出しても現在のコードと
  一致し、`altAzToEquatorial`もN/E/S/W個別にastropyと一致済みなので、bと違って
  ここにはまだ具体的な不整合は見つかっていない。
- (b) ステップ5(`skyLock.ts`の`update()`: カメラへの反映)側の180°回転バグ。
  リングは`directionForAltAz`を直接使うだけでステップ5を経由しないため、
  「実際の空と同期」中にカメラとリングを見比べて感じた違和感が、実は
  リングではなくカメラ側(ステップ5)の問題である可能性がある。

**問題**: 現状、コンパスリングは`skyLock.enable()`(=カメラ自動制御ON、
`controls.enabled=false`)でしか表示できないため、(a)リング自体の正しさと
(b)カメラの反映を、自由視点で切り分けて比較する手段がなかった。

### ステップ4b検証用(実装済み): リング単体表示モード(自由視点)

`viewer/src/ui/ringCheckButton.ts`(新規)。「コンパスリング表示(自由視点)」
ボタンを押すと、`skyLock`を一切介さず(`controls.enabled`はそのまま)、
位置情報だけ取得してコンパスリングを表示する。ドラッグで自由に視点を回しながら、
`#heading-check-panel`(方位チェック、実機の生センサー値で確認済み)を
同時に見て、リングの「N」ラベルにカメラを向けたときに方位チェックパネルが
本当に北(0°付近)を示すかを確認できる。

- 一致する → ステップ4b(リング自体の座標変換)は正しい。
  E/W・N/S入れ替わりの原因はステップ5(カメラへの反映)にある。
- 一致しない(例: リングの「N」を向いているのに方位チェックは東や南を示す) →
  ステップ4b(またはステップ3)にまだ別のバグが残っている。

### ステップ5(バグ発見・修正済み): カメラへの反映

リング単体表示モードで検証したところ、「コンパスリングのNは画像上の北極星
方向を正しく向いている(=ステップ4bは正しい)。しかしスマホが南を向いたとき、
カメラには北の空が表示される」との報告。ステップ4bが正しいと確定した以上、
バグはステップ5(`skyLock.ts`の`update()`: `targetObject.lookAt()` →
`currentQuaternion.slerp()` → `camera.quaternion.copy()`)に確定した。

**原因**: Three.jsの`Object3D.prototype.lookAt()`のソース
(`three/src/core/Object3D.js`)を確認すると、対象が`isCamera`かどうかで
内部の計算式が入れ替わる仕様になっている:

```js
if ( this.isCamera || this.isLight ) {
  _m1.lookAt( _position, _target, this.up );   // カメラ/ライト用
} else {
  _m1.lookAt( _target, _position, this.up );   // 通常オブジェクト用(eye/target逆)
}
```

`skyLock.ts`の平滑化用`targetObject`は`new THREE.Object3D()`(通常オブジェクト)
だったため、`targetObject.lookAt(direction)`は`else`分岐に入り、意図した
「カメラの位置から`direction`を見る」向きの**正確に180°反対**の向きを
計算していた。

**検証**: ブラウザ上で同一の`direction`・`position`に対し
`new THREE.Camera()`と`new THREE.Object3D()`それぞれで`.lookAt()`した結果を
比較したところ、両者は`quaternion.angleTo()`でちょうど180°、前方ベクトルは
完全に符号反転していることを確認した(`new THREE.Camera()`版は実際の
`PerspectiveCamera.lookAt()`と完全一致)。

**修正**: `targetObject`を`THREE.Object3D`から`THREE.Camera`
(`isCamera=true`を持つ最小クラス)に変更(`skyLock.ts`)。

### 追加報告: panは改善したがtiltがまだおかしい

上記修正後、「pan方向は良くなった。tilt方向の挙動がまだおかしい。lookAtに
視点移動を丸ごと任せていないか、カメラの回転とスマホの姿勢をちゃんと
同期させる処理になっているか」との指摘。

**原因**: `skyLock.ts`の`update()`で`targetObject.up.copy(this.camera.up)`と
していたが、`camera.up`は**Three.jsのワールド座標系の固定Y軸**であり、
実際の観測者の天頂(真上)とは何の関係もない。`lookAt()`の`up`引数は
「カメラのロール(画面の傾き)をどちらを基準に解決するか」を決めるパラメータ
なので、無関係な固定軸を渡すと、方位角(pan)が合っていても仰角(tilt)を
変えるとロールが不正確に揺れる。

**検証**: 東京の緯度経度・任意時刻で実際の天頂方向を計算し、固定の
`(0,1,0)`との角度差を求めたところ**約61°**もズレていた(些細な誤差ではなく、
常に大きくロール計算が狂っていたことになる)。水平線方向との角度は
正しく90°になっており、天頂方向自体の計算(既存の`astro/`パイプライン)は
幾何的に正しいことも確認済み。

**修正**: `targetObject.up`に、`altAzToEquatorial({altDeg:90,azDeg:0},...)` →
`equatorialToGalactic` → `galacticToWorldDirection`で求めた「実際の天頂を
ワールド座標に変換した方向」を使うよう変更(`skyLock.ts`)。

### 追加報告: tilt方向に動かすとジャンプする(固定時は正しい)

上記修正後、「pan方向は完全にスムーズでコンパスリングに沿って回転できる。
tiltもしっかり反映されるが、tilt方向に動かす際にジャンプする。固定した時の
見た目は正しい」との報告。

**原因**: `targetObject.up`を実際の天頂(alt=90, az=0の**固定1点**)にしていたが、
これは`Object3D.lookAt()`内部の`Matrix4.lookAt()`(`up`と視線方向の外積で
ロールを解決する)にとって、視線が天頂に近づく(上向きにtiltする)ほど
`up`と`direction`が平行に近づき不安定になる特異点を再導入してしまっていた。
Three.jsのソースには「upとzが平行なときは0.0001だけずらす」という
フォールバックがあり、その閾値をまたぐ瞬間に結果が不連続に飛ぶ。

**修正(誤り・revert済み)**: `up`を固定の天頂点ではなく「現在の方位角のまま
仰角だけ+1°した方向」(視線に追従する動的な基準)に変更したが、これは**逆効果**
だった。ユーザーから「症状が悪化した。前の方が綺麗だった」との報告、および
「スマホを垂直にしてpanしたときコンパスリングは水平に見えるはずか?」という
質問(答えはYes)を受けて再検証。

`lookAt()`内部の外積`up × forward`は、2つのベクトルの**なす角が大きい(直交に
近い)ほど数値的に安定し、平行に近いほど不安定になる**。動的なup基準は
常に視線から約1°しか離れていない設計だったため、**全ての仰角で**
「ほぼ平行」という不安定な条件を作ってしまい、天頂付近だけで起きていた
問題を全域に広げてしまっていた。固定された実際の天頂は、通常の視線方向とは
大きく(直交に近く)離れているため、天頂そのものを向いたとき以外は
はるかに安定していた。

**最終的な修正**: `up`を固定の天頂点(alt=90, az=0を変換したワールド方向)に戻した。
真の天頂を直視したときのみ理論上の特異点が残る(どの実装・実際のプラネタリウムアプリ
でも不可避)。

これで一連のバグ(コンパス-1値、OrbitControls干渉、南北反転、東西南北180°反転、
ロール基準の誤り)がすべて特定・修正された。tilt時のジャンプについては
「天頂そのものを直視したときのみ発生する、不可避な理論上の特異点」として
許容範囲内と判断し、これ以上のup基準変更は行わない方針。

## 回帰テストの追加

実機での確認→修正→また実機で確認、を繰り返す度に「直したつもりが別の場所を
壊していた」(動的up基準への変更が典型例)を繰り返したため、これまで発見・
検証した性質をVitestの回帰テストとしてコード化した(`viewer/`で`npm test`)。

- `astro/time.test.ts`: JD/GMST/LSTの基本的な健全性。
- `astro/coords.test.ts`: astropyとのクロスチェック(このデバッグ中に一度だけ
  実行したスクリプトの結果を固定フィクスチャとして埋め込み)、天頂での
  RA=LST・Dec=latの不変性。
- `astro/galacticToDirection.test.ts`: 北緯90°→sphere y=+1、南緯90°→y=-1
  (南北反転バグの回帰ガード)、l=0/360の連続性。
- `scene/createCompassRing.test.ts`: リング半径の一定性、N/S・E/W対蹠性、
  天頂と地平線の直交性。
- `skyCameraOrientation.test.ts`(新規`skyCameraOrientation.ts`に
  `update()`からロジックを抽出): カメラの前方ベクトルが意図した方向と一致するか
  (`Object3D` vs `Camera`の180°反転バグの回帰ガード)、up基準が視線から
  十分離れているか(数値安定性)、**スマホを垂直にしてpanしたときコンパス
  リングが水平に見え続けるか**(ユーザーからの質問をそのまま不変条件として
  コード化)。

`skyLock.ts`の`update()`は`computeSkyDirectionQuaternion()`(新規
`skyCameraOrientation.ts`)を呼ぶだけに簡略化し、平滑化・カメラへの適用のみを
担当するようにした。天文計算・カメラ向き計算の核心部分はDOM/実センサーに
依存しない純粋関数になっているため、実機なしでテスト可能。

## 追加報告: カメラのビクつき(ジッター)

3本リング追加後、「カメラのビクつきが治れば最高」との報告。原因として
以下2点を疑い、修正した:

1. **平滑化がフレームレート依存だった**: `SMOOTHING_FACTOR=0.2`は
   「毎フレーム固定20%」という割合で、実質的な時定数はフレームレートに
   依存していた(60fps前提で約75ms)。実機はフレームレートが揺れうるため、
   平滑化の効き方も毎フレーム微妙に変わり、一貫しないガタつきを生む余地が
   あった。
2. **コンパス(磁気センサー)は原理的にノイズが多い**: `webkitCompassHeading`は
   静止させていても数値が微妙に揺れるのが普通で、75ms程度の時定数では
   減衰しきれない可能性がある。

**修正**: `skyLock.ts`の平滑化を、固定割合ではなく経過時間ベースの指数平滑化
(`skyCameraOrientation.ts`の`computeSmoothingFactor(deltaSeconds, timeConstant)`)
に変更。時定数は0.15秒(従来より穏やかに)に設定。`main.ts`の`animate()`で
`performance.now()`によるフレーム間経過時間を計測し`skyLock.update(deltaSeconds)`
に渡すよう変更。`computeSmoothingFactor`はフレーム分割に関わらず同じ経過時間で
同じ収束率になることをテストで確認済み(`skyCameraOrientation.test.ts`)。

## コンパスリングを3本のギズモ風リングに拡張

地平線リング(pan)だけでなく、天頂/天底とN/S・E/Wを通る子午線リング
(それぞれtilt・roll方向を可視化)を追加(`scene/createCompassRing.ts`)。
3DCGソフトの回転ギズモのように、3本の互いに直交する大円が常時表示される。
天底ラベル(`z`、小文字でZenithの`Z`と区別)も追加。`createCompassRing.test.ts`
に3本のリングの直交性・子午線が天頂/地平線/天底を正しく通ることの
回帰テストを追加済み。

## 追加報告: 方位角そのものがジャンプしている(磁気センサーの外れ値)

ジッター修正後の画面収録で、「方位角も連動してジャンプしていた」との報告。
これは平滑化(表示側)の問題ではなく、生のコンパス値(磁気センサー)自体が
瞬間的に外れ値を返している可能性が高いと判断した。実機の磁気センサーは
屋内の金属・電子機器などによる磁場干渉に敏感で、`webkitCompassHeading`が
一瞬だけ大きく外れた値を返すことがある。`-1`の無効値センチネル
(既に除外済み)とは別に、「有効な値だが一瞬だけ大きくズレている」ケースは
これまでフィルタしていなかった。指数平滑化はこの外れ値も一旦目標として
受け入れてしまうため、ジャンプして戻る、という見え方になっていたと考えられる。

**修正**: 新規`sensors/headingOutlierFilter.ts`に、方位角(azDeg)の外れ値
フィルタを実装。1フレームで45°を超える急なジャンプは一旦保留し、
次の1サンプルで同じ方向のジャンプが再度観測された場合のみ「本物の
素早い旋回」として受け入れる(2回連続で同じ方向に外れない限り、直前の
採用値を使い続ける)。DeviceOrientationイベントは人間が物理的に振り向ける
速さよりずっと高頻度で発火するため、この閾値は本物の動きを誤って
リジェクトすることはほぼない。`sensors/deviceOrientation.ts`の
`DeviceOrientationTracker`内で、`computeAltAz()`が出したazDegに対して
適用し(`start()`のたびに状態をリセット)、単体テストを追加済み(通常の変化・
0/360またぎ・単発外れ値の保留・2連続確認による受け入れ、を網羅)。

## 追加報告: 仰角0°付近(SとWの間)でカメラが不安定になる

「カメラのジャンプは、少なくとも仰角0°あたりの時、SとWのちょうど間で不安定に
なる」との報告。2つの仮説を数値検証した:

1. **銀河座標の極(b=±90°)が地平線と交差している説**: 東京の緯度だと南銀極
   (SGP)がちょうど方位角236°付近(まさに「SとWの間」)で地平線をかすめる
   ことを計算で確認。しかし`galacticToWorldDirection`の出力ベクトルを
   b=-89.5°(極から0.5°)で数値検証したところ、方向ベクトルの変化率は完全に
   正常だった。**この仮説は否定**(球面座標の経度は極付近で不安定でも、
   最終的な3Dベクトルはsin(theta)→0で減衰され安定する)。
2. **センサー側のジンバルロック説**: `computeAltAz()`を単体で数値実験した
   ところ、仰角0°になるには`beta`(前後の傾き)が方位(alpha)に関係なく
   常に約90.5°になることを確認。これは`alpha,beta,gamma`のオイラー角
   (`YXZ`順)にとって典型的なジンバルロック姿勢で、この姿勢では
   alphaとgammaの役割が数学的に縮退し、OS側のセンサーフュージョンが
   実際の物理姿勢が動いていなくてもalpha/gammaの値をブレて報告することが
   知られている。

ユーザーに「地平線付近の不安定さはSW以外の方角でも起きるか」を確認した
ところ「全方位でおきます」との回答。方位に依存しないことが確認できたため、
**仮説2(ジンバルロック)が確定**。「SとWの間」という報告は、たまたまその
方角を向いてテストしていただけで、コード側に方位依存の欠陥があるわけでは
ない。

**修正**: 方位角専用だった外れ値フィルタ(`sensors/headingOutlierFilter.ts`)
を汎用化し、`sensors/outlierFilter.ts`に統合。`filterOutlier(state, rawDeg,
deltaFn)`という形にして、円環量(方位角、`circularDeltaDeg`)と線形量
(仰角、`linearDeltaDeg`)の両方に同じロジックを使えるようにした。
`deviceOrientation.ts`の`DeviceOrientationTracker`で、azDegだけでなく
altDegにもこのフィルタを適用(別々の状態を保持)。

あわせて、単発外れ値を「次の1サンプルで確認」という仕組みだけでは、
ジンバルロック起因のノイズが2つの値の間を交互にバウンスするケース
(bistableノイズ)で永久にフィルタが固まってしまうリスクに気づいたため、
一定フレーム数(5フレーム)以上保留したら強制的に採用する安全弁を追加。
`outlierFilter.test.ts`に、通常のケースに加えてこの安全弁の単体テストも
追加済み(51件全パス)。
